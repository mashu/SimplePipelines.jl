Resource limits and safety

A pipeline must never freeze your computer. SimplePipelines therefore runs every command under a resource guard: a small separate process, started by the first run, that measures each command the pipeline starts and stops the ones that use too much memory or time. It works even while Julia itself is busy, and it kills everything the pipeline started if Julia is interrupted or dies. There is nothing to set up.

Declaring what a step needs

@rule sort_bam("bam/{s}.bam" => "sorted/{s}.bam"; threads=4, mem_mb=8000, timeout=3600) =
    "samtools sort -@ {threads} -m 1500M -o {output} {input}"
  • threads: CPU slots the step takes (default 1). {threads} in the template is this number, and its commands see OMP_NUM_THREADS, OPENBLAS_NUM_THREADS, MKL_NUM_THREADS, RAYON_NUM_THREADS, JULIA_NUM_THREADS, GOMAXPROCS and similar variables set to it, so multithreaded libraries do not start one thread per core in every step. These variables are advice that a tool may ignore; pass {threads} to tools that take a thread flag. nproc follows OMP_NUM_THREADS, so $(nproc) in a script equals the step's threads.
  • mem_mb: the step's memory limit in MiB. The step starts when that much fits in the free memory not promised to running steps (or alone, when nothing else runs and memory is not low), and it is terminated if its processes use more (:memory_limit). {mem_mb} in the template is the same number. Give the tool about 80% of it, because tools need memory beyond their own setting, and per-thread settings multiply: samtools sort -@ 4 -m 1500M may use 4 × 1500 MiB.
  • timeout: seconds. A command still running after that long is terminated (:timed_out). Julia functions cannot be stopped: wrap such a step in a Timeout to stop waiting for it (it is abandoned and its resources freed).

with_resources(node; threads, mem_mb, timeout) sets defaults for every step inside node that does not declare its own.

What the guard does

situationwhat happens
a command uses more memory than its mem_mbterminated within a fraction of a second; the step fails with :memory_limit
a command runs longer than its timeoutSIGTERM, then SIGKILL 5 s later; the step fails with :timed_out
a Timeout node expiresits commands are terminated; its steps that have not started never start
free memory gets lownew steps wait (⏸ waiting for memory); if it stays low for 120 s while nothing of the pipeline runs, the waiting steps fail with :out_of_memory instead of waiting forever
free memory keeps fallingthe pipeline's own commands are stopped, those using more than they declared first, and queued again when memory is free (↺); a step that does not fit even when it runs alone fails with :out_of_memory
other programs use the memorynothing is stopped; the run waits and says so
a step leaves background processes runningthey are terminated and the step fails
Ctrl-C, the terminal is closed, Julia is killedevery command the pipeline started is killed

Memory is measured per step, summed over every process the step starts, as memory the system cannot reclaim: anonymous memory, shared memory and swap. Page cache from reading large files does not count. Free memory takes container and cgroup limits into account (Docker, Slurm, Kubernetes, systemd), so the pipeline stays inside the allocation of a cluster job.

Steps that declare no mem_mb have no per-step limit, but they are measured and protected like the others: they are charged 256 MiB when they start, and they are the first to be stopped when memory runs out because they use more than they declared. Declare mem_mb for memory-hungry tools so they start only when there is room for them.

StepResult.peak_mb holds each command's peak memory, and the log shows it: ✓ align[s=A] (12.3s, peak 3.2 GiB). Use it to choose mem_mb.

Run settings

run(pipeline; jobs=16, mem_mb=64_000, min_free_mb=0, nice=10, guard=true)
keyworddefaultmeaning
jobsCPUs this process may useCPU slots; a step takes as many as its threads
mem_mb80% of the memory this process may usebudget for the steps running at once, in MiB (0: none); a step's mem_mb above it is lowered to it
min_free_mbautomatic: 5% of memory, between 256 and 2048 MiBmemory to keep free: below twice this new steps wait, below it commands are stopped
nice10priority of commands (0–19), so the computer stays responsive
guardtrue (false on Windows)false runs without the guard: no memory limits, step timeouts or memory-pressure handling, and no cleanup if Julia is killed; Timeout nodes and the cleanup at the end of each step still work

The CPU and memory defaults follow the process's CPU affinity and cgroup limits, so jobs and mem_mb are right inside containers and cluster jobs.

Julia code

Julia function steps run inside your Julia session. Their mem_mb is reserved when they start but cannot be enforced, and they cannot be stopped. Put heavy Julia work in a script and run it with julia:

@step counts("reads.tsv" => "counts.tsv"; threads=4, mem_mb=8000) =
    julia("--project=scripts scripts/count.jl {input} {output}")

The script runs in a new Julia process: this Julia, the active project, --threads={threads} and a --heap-size-hint below mem_mb, followed by your arguments (your flags win). It is limited, measured and stopped like any command. The paths are in ARGS.

Commands started with run(...) inside a Julia function belong to your Julia session and are not tracked; return the command from the function instead, and the step runs it.

Rules for commands

  • A step ends when all its processes have exited. If the main command finishes and leaves processes behind, they are terminated and the step fails: end scripts that start background jobs with wait.
  • Commands have no terminal: stdin is /dev/null, so a tool waiting for input fails instead of hanging.
  • Commands run at nice 10 and are the system's preferred victims if it runs out of memory despite everything, so Julia and your desktop survive.
  • An output process substitution such as tee >(sort > x) is not waited for by bash, so a still running sort counts as a leftover. Write to a file and process it in a following command instead.
  • A process that must outlive the step does not belong in a pipeline step. One that escapes anyway (below) must not keep the step's output open: the step then fails instead of hanging.

Limits

  • Linux has every guarantee above. On macOS timeouts, cleanup and Ctrl-C work, but memory is not measured. On Windows the guard is not available: runs say so and work without it.
  • Memory is sampled every 0.5 s (0.1 s near a limit), so a command that allocates very fast can overshoot briefly. If the system runs out of memory in that moment, its out-of-memory killer picks the command, which fails with :out_of_memory.
  • A process escapes the guard when it leaves the step's session and its parent exits within one sampling interval, for example a command setsid -f cmd or a daemon that double-forks. setsid -w cmd is tracked.
  • Containers started through a daemon (docker run, podman run with a service) run outside the step's processes: they get no memory limit and are not cleaned up. Use apptainer/singularity, which run as child processes, or give the container its own limit (docker run --rm --init --memory={mem_mb}m ...).
  • Files written to memory-backed filesystems such as /dev/shm count as used memory but belong to no step.
  • Several runs at the same time in one Julia session share the guard but not their budgets.
  • The guard is one small Julia process per Julia session: it starts in about 0.4 s with the first run, uses about 120 MiB of its own memory (about 210 MB resident, most of it shared with Julia's libraries), and stops with Julia.

Failures

kindmeaning
:memory_limitthe step used more than its mem_mb; raise it, or lower the tool's own memory setting
:out_of_memorythe computer ran out of memory for this step, or the system's out-of-memory killer stopped it
:timed_outthe step's timeout or an enclosing Timeout expired
:process_failedthe command failed, left background processes running, or was killed from outside
:stoppedthe run was interrupted, or the guard exited unexpectedly
:templatea placeholder cannot be filled, such as {mem_mb} without a declared mem_mb

If the guard cannot start or exits unexpectedly, the run stops and kills its commands, because steps must not run without protection.
